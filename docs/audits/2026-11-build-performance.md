# Build performance audit, 2026-11

This audit records where sp1-lean's build time goes, why, and what was done about it. sp1-lean is an
unusual Lean workload: a generated Sail model with 300–400-way matches, about 25 structurally similar
chip proofs, Clean circuit tactics, executable checks over whole ensembles and a native exporter.
The mechanisms below are written so that other projects can recognise them.

## Method

- **Solo sweep.** `scripts/profile_compile.sh` runs one `lean` per module against a warm build,
  sequentially, with the package's flags (and each owning library's), emitting C as Lake does. Per
  module it records CPU, **instructions retired** and peak RSS (macOS `time -l`), C size and Lean's
  profiler categories. Instructions retired are the primary metric: wall time on a shared laptop is
  noise.
- **Need verdict.** `scripts/proof_closure.py` follows theorem proofs from the headline roots
  (`Shard.sail_trace`, `Shard.statement_iff`, `AdmissibleExecution`, `sp1Machine`,
  `Air.Flat.Realizes`). `scripts/profile_aggregate.py --inventory` joins both.
- **CI.** Per-step and per-job times from the GitHub jobs API; per-module `Built` lines, including
  `:c.o` native compiles, from job logs.

Caveats found on the way: Lean's profiler categories are wall-clock, so a sleeping machine charges
hours to whatever category was running (26 modules, about 8 h, in the first sweep; sweeps now run under
`caffeinate`). A module must be profiled with its owning library's options (`LeanRV64D.RvfiDii` needs
`LeanRV64DRvfi`'s `backward.do.legacy`: 6.0 T instructions without it, 23 G with it).

## Fixes landed in this campaign

| PR | Change | Measured effect |
|---|---|---|
| #197 | `execute` dispatched by per-constructor `rfl` equations instead of `simp only [execute]` | five Sail modules −85…−93 % instructions; C 4.3 MB → ≤ 56 KB each; clang 499 s → 0.09 s per file |
| #198 | stacked PRs restore their parent's build; one `lake build`; `export-rust` fan-out 4 → 18 | stacked first run no longer rebuilds about 1,290 jobs; first live run restored its parent after a 37 min wait |
| #199 | concrete decodes from `instructionDecode_agrees` instead of 18 hand-walked cascades | `SailDecode` 849 G → 51 G instructions (89 s → 3.5 s) |
| #200 | no global `simp` on `currentlyEnabled`; `eq_def` unfolds | compiled splitter code 200k → 73k lines; clang on `SailPlatform.c` 28 s → 0.1 s |
| #201 | whole-assembly checks compiled (`lake exe sp1Checks`) instead of interpreted `native_decide` | `LocalCore` 180 s → 4.3 s elaboration plus 15.8 s compiled checks, off the build's tail |

## Mechanisms

1. **Match splitters are compiled to native code.** The equations of a definition by `match` need its
   splitter; Lean generates it privately in each module that first needs the equations and also runs
   `compileDecl` on it (`Lean/Meta/Match/Match.lean` `mkMatcher`, `MatchEqs.lean`). For a
   361-way match that is an 80,000-line C function per module. A core-Lean reproduction (a
   200-constructor inductive and one `simp only [f]`) emits 2.2 MB of C.
2. **The splitter has three triggers:** `simp only [f]` (per-arm equations), a global
   `attribute [simp] f`, and simp's default `iota` handling, which asks for the equations of any
   matcher application it cannot reduce (`Lean/Meta/Tactic/Simp/Rewrite.lean` `simpMatch`). Remedies:
   per-constructor `rfl` lemmas proved once, or `f.eq_def` when every discriminant is a constructor.
3. **Clang time grows faster than function size.** 80k lines took 499 s, 21k lines 28 s: one giant
   function costs far more than several small ones.
4. **Kernel re-reduction of the same cascade.** Concrete `whnf`/`rfl` walks of a large decoder are
   re-checked by the kernel per lemma. When a general agreement theorem exists, a concrete instance is
   `agrees _ _ rfl` over the small executable function.
5. **`native_decide` interprets its callees.** Only the auxiliary declaration is compiled; everything
   it calls runs in the interpreter unless precompiled. Whole-ensemble checks belong in a compiled
   executable (same trust: both rely on the compiler).
6. **Stacked pull requests and caches.** A PR can restore only the default branch's and its own cache
   entries, so a stack after a repository-wide move rebuilds everything per PR. The parent's uploaded
   build is the right seed.
7. **Barrier tails.** Separate `lake build` calls per target each wait for their slowest module.
8. **Early cutoff stops at non-module importers.** Lake hashes only `.olean` across module→module
   imports; a non-module importer hashes the private parts too, so a proof edit still cascades through
   it (`lake/Lake/Build/Module.lean`).

## Open clusters

Per-file dossiers follow the inventory, one cluster per PR: the decode walk (`Families`), host-core
table bounds (`HostLocalCore`), per-chip reader unfolding (chip `Formal` files), grounding and
contracts (`MemoryChips`, `ChipContracts` at 9.9 GB peak RSS, `TypedTimeContracts`), the remaining
interpreted test modules, the generated model's codegen (`LeanRV64D.Defs` emits 10 MB of C), module
mode for early cutoff (#33), and asynchronous elaboration of inline proof fields.
